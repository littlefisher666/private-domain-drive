## 2. 背景与问题定义

### 2.1 当前背景

用户希望拥有一个适合小范围熟人使用的共享文件工具，核心诉求是：

- 文件统一存放在阿里云 OSS
- 成员数量少，预计不超过 5 人
- 总存储规模约 50GB
- 需要 Android 和 macOS 双端可用
- 不希望搭建传统重后端
- 不希望维护复杂用户体系、数据库和细粒度权限模型

现有商业网盘的问题：

- 指定成员共享文件夹的形态不完全符合预期
- 会员费用和功能打包不一定匹配小规模私人场景
- 数据与权限规则不可完全自定义
- 偏公开链接分享，不适合长期固定成员共享

### 2.2 核心问题

如何以较低成本构建一个轻量、可控、可跨端使用的私人共享文件 App，在不引入重型后端和复杂基础设施的前提下，满足小范围文件共享、上传、下载和预览需求。

### 2.3 目标用户

- 主用户：愿意自行管理云资源的个人开发者，或家庭/熟人群体组织者
- 次用户：被邀请加入共享空间的家人、朋友或固定协作者

## 3. 产品目标

### 3.1 目标

- 支持 Android 和 macOS 访问同一共享文件空间
- 支持固定少量成员共同使用
- 支持文件浏览、上传、下载和基础预览
- 尽量不依赖传统 ECS、常驻服务和数据库
- 控制云资源成本
- 保持权限模型简单
- Android 端符合手机使用习惯
- Android 支持从系统相册/系统分享批量导入图片，并在 App 内选择上传目录
- macOS 与 Android 支持多选文件并批量下载、批量删除；批量下载以独立文件任务呈现进度

### 3.2 非目标

- 替代成熟商业网盘
- 公开注册与大规模多租户
- 精细到文件级/成员级的复杂权限编排
- 视频转码、Office 在线编辑、秒传、内容审核等重能力
- 完整后台管理系统

## 4. 方案定位

本产品定位为：

`一个基于阿里云 OSS 的轻量私人共享文件 App`

不是：

`一个完整商业网盘`

因此一期优先满足：

- 小规模可用
- 成本可控
- 架构简单
- 维护门槛低

## 5. 需求范围

### 5.1 In Scope

- 成员登录与身份识别
- 获取临时访问凭证
- 浏览共享文件空间
- 创建和查看文件夹
- 上传、下载文件
- 预览图片 / PDF / 文本
- 基于权限显示可用操作
- 基础传输任务与错误反馈
- Android 系统分享接入与目标目录选择
- Android / macOS 平台差异化基础体验

### 5.2 Out of Scope

- 对外公开分享链接管理
- 复杂邀请流程
- 站内消息、评论、标签、收藏
- 回收站、版本历史、审计日志中心
- 在线协同编辑
- 视频在线播放转码
- 复杂搜索
- 数据库驱动的成员/角色后台

## 6. 用户场景

### 6.1 家庭共享

家庭成员共同访问照片、证件扫描件、家庭文档等内容。

### 6.2 熟人资料共享

2 到 5 人小群体共享学习资料、项目资料或常用文件。

### 6.3 多设备访问

Android 上查看和上传，macOS 上整理目录、批量下载和拖拽上传。

### 6.4 相册批量分享上传

在系统相册批量选图，通过系统分享进入 App，选择目标文件夹后上传。

## 8. 产品方案摘要

### 8.1 总体思路

- 文件存储：阿里云 OSS
- 身份与授权：阿里云 RAM / STS
- 轻量后端：阿里云函数计算 FC
- 客户端：Flutter（Android + macOS）

### 8.2 关键原则

- 不在客户端长期保存高权限永久密钥
- 文件上传下载不经业务服务端中转
- App 负责能力展示，云端负责最终鉴权
- 一期不做重后台、重数据库、重协作

技术细节见 [技术文档.md](./技术文档.md)。

## 10. 非功能要求摘要

### 10.1 性能

- 登录后文件列表首屏尽量 3 秒内完成
- 常规小文件传输稳定
- 列表滚动流畅

### 10.2 可用性

- 不把阿里云底层复杂概念直接暴露给普通成员
- Android 与 macOS 信息结构一致，交互允许平台差异
- 操作反馈明确：加载、成功、失败、重试

### 10.3 安全性

- 使用临时凭证访问 OSS
- 不持久化高权限永久密钥
- 删除需二次确认

### 10.4 成本

- 不引入传统 ECS 作为一期基础设施
- 尽量避免数据库作为一期依赖

## 11. 成功指标

- 5 人以内成员可稳定登录并访问共享空间
- 上传、下载、预览主流程可稳定完成
- Android 与 macOS 均可完成核心闭环
- Android 可通过系统分享完成“选图 → 选目录 → 上传”
- Android 主要页面无明显主题/交互割裂
- 无需 ECS 与数据库即可运行一期

## 12. 风险与应对摘要

| 风险 | 应对 |
| --- | --- |
| 客户端误判权限 | 最终鉴权放在 OSS/RAM；客户端仅做展示收敛 |
| 凭证泄露 | 使用短时 STS，不嵌长期高权限密钥 |
| 双端文件能力差异 | 提前验证选择器、拖拽、分享、保存路径 |
| 弱网传输失败 | 分片上传、重试、任务状态可见 |
| 需求膨胀成完整网盘 | 严格守住一期范围，先打通轻量闭环 |

## 13. 分期建议

### 13.1 第一阶段：最小可用

- 登录与临时凭证
- 文件列表与基础目录操作
- 上传、下载、预览
- Android / macOS 基础适配
- Android 系统分享导入
- Android 移动端体验统一

### 13.2 第二阶段：体验增强

- 更完整的任务管理
- 更稳的缓存与弱网体验
- 更清晰的目录管理
- 更细的错误提示

### 13.3 第三阶段：按需扩展

- 成员管理增强
- 分享链接
- 备注/标签
- 操作日志
- Windows 端

## 14. 开发前确认项

- 登录方式最终选型
- RAM / STS 授权模型
- 是否需要 API 网关
- Flutter 双端关键插件兼容性
- 上传/下载/预览最小文件类型范围
- 删除能力是否向全部成员开放
- Android 系统分享一期是否仅图片，或图片 + 通用文件
- 分享进入时默认目录策略：最近目录 / 固定 uploads / 强制自选

## 15. 结论

私域网盘一期应做成“轻量、可控、够用”的小范围共享文件产品，而不是小而全的商业网盘。
