# Design

## 现状

- `AppController._moveToRecycleBin` 以"一次调用一个批次"为粒度：`deleteItem` 与 `deleteBatch` 都把全部源对象集合一次性复制到 `shared/.trash/<id>/payload/`，写单个 manifest（name 为「已删除项目」/「已删除 N 项」），再批量删除源对象。
- `RecycleBinPage._itemsFor` 以 `recycleBinPath`（默认 `shared/`）为根，把每个批次的对象源路径展开成虚拟目录树，批次按"源路径第一段"聚合为虚拟文件夹。

## 目标模型

- 每个被删除的顶层条目（文件或文件夹）对应一个回收条目。`RecycleBinEntry` 结构不变（id/name/originalPath/isDirectory/deletedAt/objects），manifest 格式保持兼容。
- 条目展示名：默认取被删项的原文件名；与回收站既有条目重名时追加时间戳——文件插在扩展名前（`报告_20261015153045.pdf`），文件夹直接追加（`资料_20261015153045`）。取当前时间生成，仍冲突时以新时间戳加序号重试直到唯一。
- 回收站根层平铺展示全部条目，以 `entry.id` 作为虚拟条目唯一 key（不同条目原路径可能相同，不能用原路径做 key）；文件夹条目可点击进入，按该条目 objects 的源路径前缀继续展开虚拟目录树（复用现有 `recycleBinPath` 钻取机制，语义不变）。
- 恢复与立即删除保持按条目整体执行；恢复时原路径冲突仍用「已还原」命名。

## 关键决策

1. **多选删除逐项建条目**：`BatchDeletePreview` 增加 `items` 字段携带选中条目；`deleteBatch` 按条目从 `objectPaths` 分组（目录按前缀、文件精确匹配），同一 key 只归属一个条目，避免嵌套选中（同时选中父目录与其子项）导致重复搬运。重试失败项时从失败路径合成单对象条目。
2. **复制与删除的时序**：复制阶段逐项进行（进度跨条目累计），manifest 逐项写入；删除源对象延后到全部条目复制完成后统一按 `_batches` 批量执行，保持既有 deleteMany 调用口径与部分失败反馈。
3. **重名判定**：删除开始时读取回收站全部既有 manifest 的 name 集合一次，批量删除内逐项占位更新，避免同批内同名条目撞名。
4. **时间戳格式** `yyyyMMdd_HHmmss`；同一秒内同名冲突（如同批多选删除两个同名文件）以重新取时 + 序号兜底。
5. **存量批次条目兼容**：旧 manifest 无新增字段，仍按单个条目渲染（name 原样展示；isDirectory 或 originalPath 以 `/` 结尾时按文件夹渲染并可钻取），恢复/彻底删除照常可用，无需数据迁移。

## 非目标

- 不做回收站内条目重命名、移动或自定义排序。
- 不改 OSS 生命周期规则；条目内对象创建时间一致，现有按对象创建时间清理的规则继续适用。
- 不做恢复冲突的自动合并。
