# Design

## Context

见 `proposal.md`。与实现相关的现状：

- 文件工作区在多选状态使用 `BatchSelectionBar` 展示下载、移动、删除；Android 长按进入多选。
- 网盘文件只存在于 OSS，分享前必须有本地副本；现有下载会进入传输中心并让用户选择目标目录，不适用于分享。
- 已有预览缓存 `DiskDocumentCache` 和相册原图缓存，但键空间、文件命名和清理策略都服务于各自场景，不能直接作为分享输入。
- `share_plus ^13.3.0` 已在依赖中，相册原图分享已在用；Android 侧插件自带 `ShareFileProvider`，无需修改 Manifest。
- 分享仅在 Android 提供；macOS 保持现状。

## Goals / Non-Goals

**Goals:**

- Android 文件工作区支持将单个或多个文件通过系统分享面板发送到微信、飞书等应用。
- 分享准备过程有进度、可取消，失败不影响文件页状态。
- 分享产生的本地缓存有明确的生命周期，不进入传输中心，不写入系统相册。
- 复用现有依赖与下载能力，保持一期最小改动。

**Non-Goals:**

- macOS 分享入口。
- 文件夹分享或打包（ZIP）分享。
- 公开分享链接、服务端分享地址或分享权限管理。
- 自定义 Android 原生分享通道以规避 `share_plus` 的缓存复制。
- 在传输中心展示分享准备进度或保留分享历史。

## Decisions

### 1. 复用 `share_plus`，不新增原生分享通道

使用 `SharePlus.instance.share(ShareParams(files: localPaths.map(XFile.new).toList()))` 调起系统分享面板，单文件与多文件走同一入口。

- 理由：依赖已存在，相册已有成功用法；Android 的 `ACTION_SEND`、FileProvider 与 URI 授权由插件处理，客户端不需要新增清单声明或权限。
- 备选：自定义 MethodChannel + 自有 FileProvider 可直接暴露 content URI，避免二次拷贝；但需要更多 Android 代码和测试，一期不采用。
- 已知代价：插件会把文件复制到 `cache/share_plus` 后再分享，大文件会额外占用磁盘并增加准备时间；通过进度反馈和失败提示兜底。

### 2. 分享入口放在批量操作条与单个文件更多菜单，由页面层统一判定可用性

在 `BatchSelectionBar` 增加 `onShare`，只在满足以下全部条件时传入非空回调并展示入口：

- 运行平台为 Android；
- 当前身份具备 `download` 能力；
- 选中项至少一个，且全部为普通文件（不是文件夹、不是别名）；
- 不处于回收站页面。

单个文件的更多菜单在 `canShare(item)` 为真时展示「分享」，复用同一分享流程；macOS 因平台条件不满足不会出现入口。

入口逻辑放在工作区页面/操作扩展中，避免把平台和权限判断散布到组件内部。macOS 不传 `onShare`，因此不会渲染。

### 3. 使用独立分享缓存，保留原始文件名

新增 `ShareCacheStore`，根目录为 `getTemporaryDirectory()/pdd_share_cache`，结构为：

```text
pdd_share_cache/<sha256(objectPath|versionToken)>/<原始文件名>
```

- 目录哈希包含对象路径和 `FileItem.objectVersionToken`，对象更新后不会复用旧副本。
- 子目录内保留原始文件名，确保微信/飞书收到的文件名正确；不能像 `DiskDocumentCache` 那样直接用哈希作为文件名。
- 命中条件：文件存在且长度与 `FileItem.size` 一致（大小未知时以存在为准）；命中时更新文件修改时间作为最近访问时间。
- 未命中时先写入 `<文件名>.part`，完成后重命名，失败或取消删除临时文件。
- 不复用 `DiskDocumentCache` 与相册原图缓存：前者文件名不可用于分享且键空间面向预览，后者与相册模块耦合且生命周期不同；分享缓存独立后规则更简单。

### 4. 分享准备使用独立进度弹窗，不进入传输中心

分享下载直接调用 `OssClientTransfer.downloadToFile`，逐个文件准备本地副本，使用独立任务 id 和取消标志：

- 多文件按选择顺序依次准备：已命中缓存的文件直接复用，未命中才下载，避免并发下载抢占带宽。
- 弹窗展示当前文件名、批次序号（多文件时）、批次累计已传输/总字节和进度条，支持取消；总大小未知时使用不确定进度。
- 每次准备开始前执行一次缓存清理；批次内已准备的副本不参与清理。
- 取消后中止当前原生下载、清理 `.part`，已完成下载的文件保留在缓存中可复用，关闭弹窗并保留选择。
- 不创建 `TransferTask`，不写入 MediaStore，避免污染传输历史和系统相册。
- 分享准备期间设置页面级 `_sharing` 标记，防止重复触发。

### 5. 分享结果只区分成功、取消和异常

`ShareResultStatus.dismissed` 视为用户取消，不提示错误；`unavailable` 与平台异常统一提示“分享失败”，不改变选择状态。分享面板关闭后不做额外跳转。

### 6. 分享缓存按时间与容量清理

- 常量：保留期 7 天、容量上限 2 GB。
- App 启动时异步触发一次清理；每次分享准备前再执行一次，保证容量有界。
- 扫描缓存目录，以文件修改时间作为最近访问时间；超过保留期直接删除；容量超限时按最旧优先删除，跳过本批次待分享文件与 `.part` 临时文件。
- 仅删除本地文件，不触碰 OSS；临时目录被系统回收时按缓存未命中重新下载。
- 不引入 WorkManager、定时任务或数据库记录。

### 7. MIME 由 `share_plus` 按扩展名推断

不新增 MIME 依赖，也不手工维护完整映射表。`share_plus` 内部使用 `lookupMimeType(path)`，未知扩展名回退为 `application/octet-stream`，仍可调起分享面板。接收方是否接受某类型由其自身决定。

## Risks / Trade-offs

- [`share_plus` 二次复制大文件导致等待和磁盘占用翻倍] → 展示真实进度，失败时明确提示；一期不设硬性大小上限，后续如有需要再引入原生 content URI 分享通道。
- [`cache/share_plus` 在每次分享前被插件清空] → 分享缓存独立于插件目录，重复分享无需重新下载；同一时间只允许一个分享准备流程。
- [系统分享面板出现“私域网盘”自身（应用已注册 `ACTION_SEND` 接收）] → 接受为一期已知瑕疵；不为此引入自定义通道，后续可评估排除自身组件。
- [临时目录可能被系统清理] → 视为缓存未命中，重新下载即可，不影响正确性。
- [对象名包含特殊字符导致本地文件名异常] → 使用对象路径最后一段作为文件名，写入前替换路径分隔符等非法字符；哈希目录隔离冲突。
- [分享准备期间应用退到后台导致下载中断] → 按失败处理并清理临时文件，保留选择，用户可重试。
- [缓存清理与正在进行的分享竞争] → 清理跳过 `.part` 和当前分享文件；页面层禁止并发分享。

## Migration Plan

无数据迁移。功能随客户端版本发布，入口仅在 Android 新版本出现；如需回滚，移除入口回调即可，已产生的分享缓存会按清理策略自然淘汰。

## Verification

- 单元测试：分享缓存命中/未命中、版本变化、取消与失败清理、超期与容量清理。
- Widget 测试：Android 单文件与多文件且有下载权限时展示分享入口；文件夹、别名、混合选择、无权限、macOS 不展示；单个文件更多菜单展示分享。
- 真机验证：Android 分享单个与多个文件到微信与飞书；取消准备；取消系统面板；离线失败；大文件进度与失败提示；重复分享命中缓存。
