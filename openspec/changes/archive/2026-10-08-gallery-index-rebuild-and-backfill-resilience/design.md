# 设计：相册索引手动重建入口与存量缩略图补齐可靠性强化

## Context

相册索引以本地 SQLite 副本 + OSS 清单对象（`.gallery/index/photos.json`，读-改-写 + ETag 乐观并发）双层维护。增量写索引仅挂钩"本客户端上传成功"时刻；旧版本客户端上传的媒体因此游离于索引之外，且自动触发全量重扫的条件（本地无索引、清单损坏、待修复标记）都不会命中。存量缩略图补齐为串行 for 循环、无超时、网络错误即跳过。

实测（macOS 端、3121 条媒体、93 个视频）暴露三个问题：单个挂起的 OSS 截帧请求堵死整个补齐队列（17 分钟零进展且无错误提示）；本机到 OSS 直连链路偶发 SSL 握手瞬断导致条目补齐失败；用户对漏索引照片无自助修复入口。

## Goals / Non-Goals

**Goals**

- 用户可主动触发一次全量重扫补齐漏索引媒体，其他设备经清单版本提升自动受益
- 单个补齐请求挂起或瞬断不再影响其余条目的补齐
- 补齐吞吐提升（并发工作池）

**Non-Goals**

- 不改变索引数据结构与清单格式
- 不改变"每次会话最多补齐一轮"的触发节奏
- 不引入 OSS 服务端事件（如Bucket 事件通知）做增量索引对账
- 不做补齐进度的界面可视化（后台静默进行，成功条目逐个刷新）

## Decisions

**1. 手动重建复用既有全量扫描，不新增扫描变体。** `rebuildIndex()` 直接调用既有 `_runFullScan` 路径（与首次建索引、待修复重建共用），未变化条目按大小+修改时间复用跳过解析，网络开销集中在漏索引条目。备选方案是独立的"差量对账"（只列举清单外的对象），但需要新增一条与全量扫描并行的代码路径，对账边界（删除、改名、覆盖）处理复杂度高，收益不成比例。入口在扫描中防重：直接复用 `GalleryPhase.scanning` 状态判断，不引入新锁。

**2. 并发用固定 worker 工作池（4 路），沿用全量扫描的成熟模式。** 条目数少（实测 26 个），不需要更大的池；补齐与用户主动传输共享带宽，4 路是有意压低的上限。Dart 单线程模型下 cursor 自增无数据竞争，与 `fullScan` 的 worker 池实现一致。

**3. 单条整体限时 90 秒（`.timeout` 包住截帧→临时文件→上传全链路），而非给每个网络调用单独设超时。** 单条超时的目的只是防挂起堵队列，不是精确的传输时限；单点超时需要改 OSS 客户端多层（截帧、下载、上传各自语义不同），复杂度不匹配。被超时放弃的条目无副作用：缩略图对象未上传则索引不更新，下次会话重试。

**4. 仅对 `OSS_NETWORKUNAVAILABLE` 做 3 次指数退避（1s/2s/4s）重试。** 实测该错误由链路瞬断引起、重试即恢复；其他错误（权限、对象不存在、参数无效）重试无意义。重试包在单条限时内，重试+限时叠加不会显著拉长整轮时长。

## Risks / Trade-offs

- [并发补齐下清单最后一次写回的条目更多，ETag 冲突概率略升] → 冲突走既有退避重试，超限标记待修复由下次全量扫描自愈，行为与既有口径一致
- [90 秒限时可能砍掉慢但最终能成功的超大图补齐（原图下载+本地缩放）] → 该条目留待下次会话重试；后续如出现普遍误杀可调大常量或对下载环节单独计时
- [手动重建在多设备并发触发时双方各自写清单] → 清单写入本身带 ETag 乐观并发，冲突方重试后收敛到同一份扫描结果，无数据丢失
- [重建入口可能被用户当作常规刷新频繁使用] → 全量扫描有断点复用，重复触发的网络成本可控；界面在扫描中禁用入口

## Migration Plan

纯客户端行为新增，无数据迁移。旧清单格式不受影响；清单版本由重建写入自然提升。回滚即回退客户端版本，本地索引与清单保持兼容。
