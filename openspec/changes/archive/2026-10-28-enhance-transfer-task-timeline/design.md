# Design

## Context

传输中心已用统一任务模型承载上传与下载，队列在 `TransferQueue` 中完成调度、状态迁移、进度节流与历史持久化。当前任务模型没有任何时间字段，速度由 `_TransferSpeedTracker` 以 2 秒窗口计算瞬时值，成功时清空；历史记录仅持久化成功与已取消任务，并以单个 JSON 字符串存放在 `SharedPreferences`，每次终态变化都会全量重写整张表。暂停与重试都会把任务重新放回等待队列，下载不支持断点续传，重新开始会从零下载。任务 `id` 中嵌入了微秒时间戳，可作为旧记录的入队时间兜底。项目已引入 `sqflite`，相册索引与目录摘要缓存均使用本地数据库。

本次变更只涉及客户端传输模块与本地历史存储，不改变 OSS 原生传输链路、并发配置、前台保活通知与上传断点续传策略。需求见 `specs/transfer-task-history/spec.md` 与 `specs/transfer-queue-management/spec.md`。

## Goals / Non-Goals

**Goals:**

- 复用已有 `sqflite` 为上传与下载任务提供可追溯的生命周期时间线与性能指标，不引入新的存储依赖。
- 历史记录按任务增量写入，避免大批量任务完成时反复序列化整张表。
- 计时与字节统计集中在队列层，UI 只做格式化展示，避免多入口重复维护。
- 历史存储向后兼容，旧记录可正常读取并展示占位符。
- 排序在重启后保持稳定，不依赖内存列表顺序。

**Non-Goals:**

- 不持久化排队中、进行中的下载任务，不新增下载断点续传。
- 不记录每次尝试的独立时间线，只保留首次时间、最近开始时间与尝试次数。
- 不提供批次汇总、按天分组、历史搜索或导出。
- 不改变 OSS SDK 进度回调口径，不引入原生侧速度统计。

## Decisions

### D1: 任务字段与语义

在 `TransferTask` 中新增以下字段，上传与下载共用：

| 字段 | 类型 | 语义 |
|---|---|---|
| `queuedAt` | `DateTime?` | 首次入队时间，重试不覆盖 |
| `startedAt` | `DateTime?` | 首次开始传输时间 |
| `lastStartedAt` | `DateTime?` | 最近一次开始传输时间 |
| `finishedAt` | `DateTime?` | 最近一次终态时间，重试时清空 |
| `activeDurationMs` | `int` | 累计实际传输时长 |
| `totalTransferredBytes` | `int` | 跨尝试累计实际传输字节 |
| `attemptCount` | `int` | 尝试次数，首次入队为 1，用户重试 +1 |

平均速度不落库，作为派生值由 `totalTransferredBytes / (activeDurationMs / 1000)` 计算。理由：避免持久化冗余字段与两者不一致；累计字节和时长本身是唯一事实来源。

备选方案是仅存时间戳、展示时用时间差计算耗时。该方案在用户调整系统时钟或跨时区时会得到错误甚至负值，因此仅时间戳使用墙钟，所有耗时使用单调时钟。

### D2: 计时与字节统计集中在队列层

`TransferQueue._runTransfer` 是任务进入与离开传输中状态的唯一位置。每次运行开始时创建 `Stopwatch`，在 `finally` 中把 `stopwatch.elapsedMilliseconds` 累加到 `activeDurationMs`，并把本次运行最终收到的字节累加到 `totalTransferredBytes`。暂停、失败、取消、成功都走同一收尾路径，避免遗漏。

- 进度回调仍只更新当前尝试的 `transferredBytes` 与瞬时速度，不参与累计值计算。
- 累计字节在本次运行结束后一次性累加，运行中不重复计入。
- 暂停后继续视为新的一次运行，累计时长与字节继续增加；`attemptCount` 不因暂停继续而增加。
- `attemptCount` 只在创建任务时置 1、用户点击重试时加 1，由控制器维护，避免把暂停继续误算为一次重试。

备选方案是在进度回调里实时累加字节。该方案需要维护每次运行的基线，且取消或失败时容易重复累加或漏加，复杂度高于在收尾时一次性结算。

### D3: 时间戳与时长分离

墙钟时间戳使用 UTC epoch 毫秒序列化，展示时转本地时区；`activeDurationMs` 使用 `Stopwatch` 统计。序列化时所有新字段可选，缺失即为未知。旧记录恢复时：

- `queuedAt` 缺失时尝试从 `id` 中解析微秒时间戳作为兜底，仅用于排序与展示入队时间。
- `startedAt`、`finishedAt`、`activeDurationMs`、`totalTransferredBytes` 缺失时按未知处理，不推算。
- `attemptCount` 缺失时按 1 处理。

### D4: 历史存储迁移到 SQLite

新增 `TransferHistoryStore`（`client/lib/features/transfer/infrastructure/transfer_history_store.dart`），复用已有 `sqflite` 打开独立的 `transfer_history.db`。表 `transfer_history` 以任务 `id` 为主键，字段与任务模型对齐，并建立 `finished_at DESC` 与 `(type, finished_at DESC)` 索引。

- 终态任务以 upsert 增量写入，不再整表序列化；失败任务纳入历史范围。
- 写操作串行化并合并：终态变化先进入待写集合，在约 300ms 延迟内以单事务批量 upsert；清空已结束任务与单条删除按 `id` 执行。
- 启动恢复异步读取第一页（300 条），滚动时继续分页查询；未结束任务仍由内存队列管理。
- 类型筛选计数由 `COUNT(*) GROUP BY type` 与内存中未结束任务合并，不依赖已加载页。
- 保留策略：启动时以及写批次后（节流为最多每小时一次）执行清理，先删除 `finished_at < 当前时间 - 90 天` 的记录，再按 `finished_at` 倒序保留最多 20000 条。
- 迁移：首次升级检查 `transfer_history_migrated` 标记，读取现有 `transfer_history:v1`，在事务内导入后写入标记；旧键保留且不再更新，作为回滚快照。
- 数据库打开或写入失败不阻断传输：仅本次历史不可用，队列继续运行。

选 SQLite 而不是继续使用 `SharedPreferences`，是因为单次上传可能包含数百个文件：JSON 全量重写在任务集中完成时会产生明显的写放大，而按行 upsert 的复杂度与历史总量无关。选独立数据库文件而不是复用相册库，是为了避免传输历史与相册索引的打开时机、账号维度绑定。

### D5: 排序改为时间驱动

状态优先级保持不变，同状态内改为：

- 未结束任务：`queuedAt` 倒序，缺失时用 `id` 解析值兜底，再相同则用 `id` 倒序。
- 已结束任务：数据库查询统一 `ORDER BY finished_at DESC, id DESC`；缺失 `finished_at` 的旧记录排在末尾。
- 加载更多只追加更旧的历史页，不重排已加载项；内存中的未结束任务始终排在已结束历史之前。

### D6: 展示层复用统一格式化

- 在传输展示层新增共享格式化函数：字节、速度、时长、绝对时间。
- 时间格式：今天 `今天 HH:mm`、昨天 `昨天 HH:mm`、同年 `MM-DD HH:mm`、跨年 `YYYY-MM-DD HH:mm`。
- 已结束卡片复用现有桌面/移动卡片布局，底部信息行改为“大小 · 耗时 · 平均速度”，第二行展示结束时间。
- 任务详情使用统一的底部弹层（桌面为对话框），内容直接读取任务字段。
- 历史列表按页加载：滚动到已结束记录底部时加载下一页并显示加载状态；没有更多记录时停止请求。
- 排队中/进行中的“已等待/已用时长”需要页面上存在定时刷新：仅当列表存在未结束任务时启动 1 秒周期定时器，列表为空或全部结束时停止，避免常驻唤醒。进行中的进度仍沿用现有 100ms 节流。

### D7: 失败记录与清除行为

失败任务纳入历史后，现有“清除已结束任务”与批量选择逻辑沿用状态判断，并同步删除数据库行。失败记录同样受 90 天与 20000 条上限约束。用户重试失败记录时，任务回到非终态并从历史表中移除；若此时应用被杀，该次重试不会留下未完成记录，这与“未完成下载不持久化”的既定范围一致。

### D8: 大批量上传的写入与展示

单批数百个文件时，每次终态变化只标记待写，由合并批次以单事务写入，避免逐条重写整表。历史保留按时间而非小数量上限，单批几百条不会挤掉其他记录。列表分页每页 300 条，足以覆盖一个典型批次，同时避免一次性把数万条记录读入内存。

## Risks / Trade-offs

- 重试会从零重新下载，累计字节包含重复下载量，平均速度会低于“有效文件大小 / 总时长”的直觉值 → 在规格中明确平均速度为实际吞吐口径，避免后续误解。
- 应用在下载中被杀时没有任何终态时间 → 不生成结束时间、不写入历史，保持现状；后续如需支持“已中断下载”需单独设计。
- 页面级 1 秒定时器可能带来额外刷新 → 仅在存在未结束任务时启用，并在页面销毁或列表清空时取消。
- 终态写入采用短延迟合并批次 → 应用在写入前被系统杀死可能丢失最后几条历史；在应用进入非活跃或暂停时主动 flush，缩小窗口。
- 迁移标记只执行一次 → 回滚到旧版本期间新增的历史在再次升级时不会补导；回滚仅作为临时兜底，长期回滚需重新评估。
- 数据库打开或写入失败 → 传输不阻断，本次历史不可用；启动时记录错误并在后续写入时重试。
- 历史保留与筛选计数随记录量增长 → 90 天窗口配合 `finished_at` 索引，清理为单条 SQL，计数结果按页面刷新缓存，避免每帧查询。
- 旧记录缺少时间字段 → 统一展示占位符，避免用当前时间伪造。

## Migration Plan

1. 扩展任务模型与 JSON 序列化，所有新字段可选并带默认值，先保证旧数据可读。
2. 新增 `TransferHistoryStore` 与 SQLite 表结构、索引，补充建表、upsert、分页查询与保留清理的单元测试。
3. 在队列收尾路径接入计时与累计字节，补单元测试覆盖成功、失败、取消、暂停继续与重试。
4. 将历史读写切换到 SQLite：启动异步加载第一页，终态批量 upsert，清除操作删除数据库行；保留 `SharedPreferences` 旧键并在首次升级时一次性导入。
5. 调整卡片展示、分页加载、筛选计数、排序与新增详情视图，补充时间格式化与占位符测试。
6. 同步更新 `docs/技术文档.md` 与 `docs/Flutter架构设计.md`。
7. 随客户端版本发布；服务端无变更。回滚时旧版本读取升级前的 `SharedPreferences` 快照，不执行数据迁移。
